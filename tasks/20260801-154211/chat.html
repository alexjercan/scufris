Lane 1 brief / release task 20260801-154211

The conversation Scufris owns

v0.2.0 stops borrowing the conversation from whichever provider answered last. A conversation is a durable thread that outlives every backend session under it, and an event is one attributable thing said inside it. Four tables and eleven functions in packages/chat, depending on scufris_core and nothing else.

What it holds

The semantic log: who said what, in what order, answering what. Not a provider transcript and not a technical activity feed.

Why it is carved out

A conversation that lives in a provider session dies with it. This one survives /new, a compaction, a backend switch and a restart.

The boundary

A schema and a store over it. No channel, no host, no agent, no model. Every function takes the caller's open connection.

The model

A thread, and the utterances inside it

Every invariant below is held by the schema or by a function signature rather than by a caller's care. That is the difference between a rule and a convention, and it is the whole reason the conversation is a package rather than a table in the app.

Durable

The conversation

An id and when it started, and deliberately nothing else. It carries no backend column: the provider session is a cache keyed by (conversation, backend, policy version), and a second home for half that key would have to be reconciled at the first switch.

Attributable

The event

One utterance, with its author already typed: an Actor over operator, orchestrator, agent:<id> and system. Ordered inside its conversation by event_seq, and pointing at the event it answers through causation_id.

Atomic

The unit of work

Every function takes an open Connection and none opens one. A caller writes its own state change in the same block as the event describing it, so the two commit together or not at all - structural, not a rule anyone is asked to keep.

InvariantHeld by
event_seq is per conversation, gap-free and strictly increasing assigned as COALESCE(MAX(event_seq), 0) + 1 inside the caller's transaction, which begins IMMEDIATE; a rolled-back write consumes no number, and UniqueConstraint(conversation_id, event_seq) is the backstop.
the author is a typed value, never a compared string Actor.parse is the one boundary a string crosses; the row carries the same rule as two CHECK constraints, so a hand-written INSERT meets the database instead.
an agent id cannot forge an attribution the id is rendered into a LINE of assembled context, so every C0 control, DEL, U+0085, U+2028 and U+2029 is refused - in the dataclass and in the CHECK's GLOB alike.
a state change and the event describing it commit together the connection-passing rule: no Database on this surface, and nothing here can open a second unit of work.
a retry after a crash cannot post a second card delivery's primary key is (channel, conversation_id, event_seq), every part derived from the event; a retry recomputes the same three values and collides with its own row.

the conversation survives the provider losing its session provider_session is a cache and the transcript is never in it; a miss re-seeds from assemble_context, and a miss is the ordinary path rather than an error.

There are no FOREIGN KEYs

A batch ALTER under foreign_keys=ON rebuilds the table the references point at. So the store checks what the schema will not: an unknown conversation, a causation_id resolving to nothing in this thread, a confirmation of something never claimed.

A miss is normal

cached_session is the one function that does not refuse an id it cannot resolve. Absent row, stale policy and unknown conversation all answer None, because the caller's response to all three is the same: assemble and re-seed.

The honest delivery guarantee

A replay of a confirmed event is an exact no-op. A crash between the send and the confirm re-sends once. Duplicated card, never a missed approval request - the collapse is the channel's job, with the channel's own affordance.

Ownership

Four records, and who writes each

One writer per record. Nothing fans out rows at append time and nothing mints an id per attempt, which is what lets a channel added next year still answer "what have I not been told" about events written before it existed.

RecordOne row isWho writes itWho reads it
conversation one durable thread: an id, and when it started. create_conversation, called by whatever starts a thread. Nothing updates one. every other record hangs off its id; the store refuses a write naming a conversation that is not there.
event one attributable utterance: an actor, a kind, a body, its position, and what it answers. append_event, inside the CALLER's transaction. The actor comes from the caller, so the guarantee is "only an operator EVENT authorizes", not "only the operator can write one". read_transcript, causing_event, assemble_context and authorize. Append-only.
delivery one channel's attempt at one event, claimed then confirmed. the channel's own pass: claim_delivery committed before the send, confirm_delivery after it returns. The send sits between two units of work, never inside one. pending_events, in one read: never-attempted events plus claimed-and-never-confirmed ones, because every caller wants that union.
provider_session one live binding to a provider's own session, under the policy it was seeded with. bind_session, on the turn that seeds a backend. An UPSERT of the one live row per (conversation, backend), overwritten in place. cached_session, which must match policy_version as well as the key. There is no invalidation function.

Where an event came FROM is not a column

delivery records where events are sent. The inbound channel of an operator message has no reader yet, and a column no code reads is a claim nothing keeps honest.

Nothing declares the set of channels

A delivery row exists only where a channel attempted, so "what has this channel not been told" is a left join - and it answers correctly for a channel that did not exist when the event was written.

The rendering is not here

assemble_context's per-line attribution is the format a PROVIDER is seeded with. A terminal or a web view reads the same Actor off read_transcript and chooses its own colours.

Settled decision

One event per meaningful thing said, not one per turn

A single turn produces several rows: the operator's message, the agent's report, a system notice. The conversation is read as an ordered transcript rather than reconstructed from turn blobs.

Chosen

The grain is one utterance

Because "who said this" decides whether an event may authorize a stop gate, and a turn-grained row cannot answer it for anything inside the turn: the operator's message and the agent's report would share one actor column.

This is the only grain where the gate's refusal is a property of the data rather than a rule the renderer follows.

Rejected

One row per turn

Cheaper to render - one row, no transcript query per view - and it is what a chat UI naively wants.

Rejected because it attributes nothing inside the turn, which is the exact defect the actor-aware spike located in the shipping code. Tool calls and agent reports are drawn as separately attributable things in the mockup this implements.

Paid

What the grain costs

A render reads N rows per turn instead of one, and the transcript query becomes the thing a later lane has to keep bounded. assemble_context is the first answer: the newest events, sliced in SQL rather than after loading the thread.

Reversal

The expensive direction

Granularity is the one choice here that is costly to undo: coarsening later means collapsing rows, and collapsing rows loses attribution. Going finer is free; going coarser is not, which is why the fine grain is the default.

kind is a plain string column rather than an enum. Nothing in the package branches on it; the enum lands with the first caller that does.

The non-decision

v0.2.0 deletes no events

There is no retention window, no compaction and no operator-visible history limit in this release. The tables grow for as long as the database lives. That is a recorded choice with a reason, not an oversight, and it is written down so a large table later reads as a known consequence.

Why nothing

The volume is not reachable

One operator on one host, and a log of semantic events rather than provider transcripts. The size that would justify a policy is not reachable inside v0.2.0.

Why not a guess

A rule now is a migration later

A retention window invented before anyone has read a month of real events would be a guess with a migration attached. Nothing in the release requires one, and no reaper has a clock to hang itself on.

Cheap to reverse

Additive, unlike the grain

A policy is a new task rather than a change to this schema. That asymmetry is the whole argument for settling granularity now and leaving retention open.

Runnable

The lane, end to end, in one script

python examples/chat_conversation.py opens a real SQLite file, writes a conversation and two events in one transaction, mints a decision from the operator's message, refuses the agent's report, delivers to two channels twice, and switches backend underneath the whole thing. Every line it prints is an assertion it already made.

The demo calls all eleven

A function exported and never exercised is a corner of the lane nothing proves, so the claim is checked as a claim: test_chat_conversation_calls_every_exported_function parses the script and compares it to __all__.

The output is asserted, not printed

The tree is rendered into a recording console and checked before it is shown, so the string the script vouches for and the string an operator reads are one string rather than two renderings that can drift.

The switch changes nothing visible

The same renderer draws the transcript before and after the backend switch, and the two must be byte-identical. The provider session id is the only thing that differs.

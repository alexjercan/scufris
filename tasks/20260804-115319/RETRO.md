## What went well

- The DoD named its six tests by name, so round 1 could check each promise
  against a specific test rather than against a feeling. That is what let R1.2
  be stated as "this named test cannot catch its own docstring" instead of as
  "coverage feels thin".
- Round 1's three lanes found the blocker by REPRODUCING the documented channel
  pass rather than reading `claim_delivery`. Every later verification in both
  rounds followed that: R1.1's fix, R1.3's CHECK text, R1.5's constraint and
  R1.6's raise were each pinned by mutation - restore the defect, watch a named
  test fail - and R2.1 was reproduced from the exported facade.
- The revision was autogenerated against the models and held there by
  `test_schema_has_no_pending_autogenerate_diff`, so no round had to argue about
  whether the shipped DDL matched the declared table.
- Records were treated as history: round 1's close-out SUPERSEDES two passages
  rather than editing them, which is why the reversal on argument order is
  legible.

## What went wrong

- **The blocker was written into the plan, not introduced by the work.** Step 4
  specifies `claim_delivery` as "`True` when this attempt minted the row,
  `False` when it was already there". That sentence IS R1.1: it makes an
  abandoned `claimed` row unclaimable forever, which is the "silently loses the
  question" failure this task's own DECISION.md section 2 rejects by name. The
  step and the decision record contradicted each other and nobody read them
  against each other. The plan then propagated the wrong contract into
  README section 5 and `examples/chat_conversation.py`, so the defect shipped in
  the SPECIFICATION - Lane 2 would have copied it - and the code was faithful.
- **The test was written from the DoD sentence, not from the caller loop.**
  `test_a_claimed_delivery_is_pending_until_confirmed` proved the state the
  design produces and reached past the loop to call `confirm_delivery` directly,
  so it could only confirm what its author already believed. That is why a green
  suite and a broken central promise coexisted.
- **Step 8 grew the branch past its subject.** Adding one migration test took
  `tests/test_db_migrations.py` to 917 lines against the 900-line cap whose
  allowlist is a ratchet, forcing a file split, a new `tests/conftest.py`
  fixture and a `scufris/README.md` edit into a delivery-table branch. The
  file's size was readable at plan time.
- **A round-1 fix left three loose ends.** R1.13's `on_conflict_do_nothing()`
  added an unreachable loser branch that would not answer if reached (R2.2);
  R1.1 and R1.6 together falsified `confirm_delivery`'s "no correct caller
  reaches it" docstring and DECISION.md section 6 (R2.1); R1.15's reflow left
  two orphan part-lines (R2.3). All three are MINOR/NIT and open.

## What to improve next time

- **Breadth.** The diff is one table plus one foreseeable split. `plan` should
  have asked what Step 8 does to the file it edits: a file within 20 lines of a
  hard cap makes the split a separate, independently landable task, and the
  delivery branch would then have been the delivery table alone.
- **Churn.** Both review rounds trace to one missing plan-time check: read each
  Step's literal contract against the task's own DECISION.md before writing it
  down. `plan/decision.md`'s cold-reader test was applied to the DESIGN (three
  columns, two states, one read) and not to the step text that implements it,
  which is exactly where the design was inverted. Walking the restart path -
  "crash after claim, restart, what does the caller get?" - against Step 4's
  sentence takes one paragraph and would have removed R1.1, R1.2, R1.4, R1.12,
  R2.1 and R2.2.
- **The from-scratch challenge.** R1.11's swapped argument orders were written
  into the plan and then DEFENDED in the close-out ("each follows its own
  neighbour") before round 1 overturned it. A close-out that has to argue for a
  shape is a signal to change the shape while no caller exists, not to record
  the argument.
- **Superseded step text.** This record now supersedes in two different ways:
  Step 8's text was EDITED in place with the deviation noted, while Steps 4 and
  6 were LEFT as planned with the close-out disclosing the change. Pick one and
  keep it - leaving the step and disclosing it reads better against
  "records are history".

## Context

Observed pressure only: round 1 ran three out-of-context lanes and round 2 one
out-of-context reviewer plus an in-session mutation and reproduction pass. No
compaction warning, checkpoint or handoff was recorded on this task. The
delegation is what kept both rounds off the implementer's assumptions, and is
worth keeping for any diff that ships a migration.

One tooling trap cost a wasted verification cycle in round 2 and is not
specific to this task: mutating a COPY of this repo and running pytest inside it
proves nothing, because the dev environment's editable install resolves
`scufris_chat` back to the original worktree and the mutant passes. `PYTHONPATH`
must point at the copy.

## Landing message

```
feat(chat): deliver chat events to every channel exactly once

Add the `delivery` table keyed `(channel, conversation_id, event_seq)`, the
three store functions over the caller's open connection, and the revision that
ships it. Every part of the key is derived from the event, so a retry after a
crash recomputes the same three values and collides with its own row instead of
posting a second card - idempotency is a property of the storage layer, so a
channel added later inherits it rather than reimplementing it.

Two states rather than a boolean: a claim before the send and a confirm after
it, so a crash mid-send leaves the delivery pending and it is retried on
restart. Exactly-once on the normal path, at-least-once across a crash.
```

# Decision: SQLAlchemy and Alembic replace stdlib sqlite3 and the user_version ladder

- DATE: 20260801-120412
- STATUS: ACCEPTED
- TASK: 20260729-102147
- TAGS: v0.2.0, reliability, storage, architecture
- SUPERSEDES: 20260801-100405 DECISION.md sections 1 and 4

## Context

20260801-100405 chose one SQLite database reached through the stdlib `sqlite3`
module, with a `PRAGMA user_version` ladder of hand-written `(version,
callable)` migrations. It listed SQLAlchemy + Alembic as a considered
alternative and rejected it on cost - two dependencies in `uv.lock` and the
uv2nix closure - while recording it as "reversible later at low cost, because
the schema is already SQL."

The user directed the reversal before any implementation started, which is the
cheapest possible moment for it: nothing is written against the stdlib API, no
migration has been authored, and no store has moved.

## Decision

The mechanism is SQLAlchemy 2.0 with Alembic. Everything 20260801-100405
MEASURED is unchanged; only the library through which it is expressed changes.

### 1. What is superseded

| 20260801-100405 said | Now |
|-|-|
| stdlib `sqlite3`, no ORM, no migration framework, no new dependency | SQLAlchemy 2.0 + Alembic, two dependencies |
| `PRAGMA user_version`, an ordered `(version, callable)` list | Alembic revisions and `alembic_version` |
| legacy JSON import rides the `user_version` ladder | import is gated on a `legacy_import` table, run after `upgrade head` |

The import moves off the version ladder because it needs `Settings.state_dir`
and pydantic validation, neither of which belongs inside a schema revision. The
policy it must satisfy does not change.

### 2. What is NOT superseded

Every measured constraint in 20260801-100405 survives verbatim: one database at
`<state_dir>/scufris.db` at file mode 0600 with its `-wal`/`-shm` siblings; the
four pragmas; `BEGIN IMMEDIATE` rather than a deferred begin; the transaction as
the read-modify-write boundary rather than a lock around the persist; no
in-memory mirror; damaged-is-not-empty with no tolerant loader; one synchronous
public API that loop-thread callers reach through `asyncio.to_thread`;
file-backed test fixtures rather than `:memory:`; the whole legacy-import policy
table; the state boundary of section 3 including its two named exceptions; and
constraint 5, that this epic creates no conversation, activity-event or
delivery tables.

Sections 2, 3 and 5 of that decision stand unamended.

## Alternatives considered

- **Keep stdlib `sqlite3` and the `user_version` ladder**, as 20260801-100405
  decided. Zero new dependencies, and every measurement in SPIKE.md was taken
  against it. Rejected by the user's direction: schema evolution stays
  hand-written callables that nothing checks against the code's idea of the
  schema, and the two follow-up store migrations each re-derive the mechanism.
- **The async SQLAlchemy engine.** Would need `aiosqlite`, which
  20260801-100405 rejected on measurement (0.28ms p50 offload cost without it)
  and which reintroduces the second async store API that decision removed.
- **SQLAlchemy Core without the ORM.** Autogenerate works from a `MetaData`
  either way. Rejected as a false economy: `Mapped[...]` models cost nothing
  extra given the dependency is already paid and give typed queries under mypy.
- **SQLAlchemy without Alembic**, with the `user_version` ladder retained.
  Keeps one dependency out but gives up the reviewable autogenerated revision,
  which is the main thing the swap is for.
- **Defer the swap until after the pilot store lands.** Rejected on cost: doing
  it now is free because nothing is written against the stdlib API yet, and
  every task deferred past raises the rewrite.

## Consequences

**Paid.** `sqlalchemy` pulls `greenlet` and `alembic` pulls `Mako` into
`uv.lock` and the uv2nix closure; `nix build .#scufris` becomes a proof on the
first two tasks. The pragma and `BEGIN IMMEDIATE` recipes become
`event.listens_for` hooks rather than two statements at connect - a pool
applies neither for free, and applying a pragma once at open is the failure mode
a pool introduces. Alembic's generated revisions need `ruff format`. The
migration environment must live at `scufris/db/migrations/` rather than a repo
root `alembic/`, because the wheel is built with `only-include = ["scufris"]`.

**Gained.** Schema evolution becomes reviewable, autogenerated revisions rather
than hand-written callables. Drift between the declarative models and the
migrated schema becomes a test. The two follow-up store migrations extend a
declarative schema instead of re-deriving a migration mechanism. Queries are
typed under mypy.

**Not a reason.** SQLAlchemy's portability to a server database. The single-host
deployment model has no plan to want one; portability here is a side effect.

**Reversal.** Unchanged from 20260801-100405: reversible until an operator
deletes their legacy JSON files, since the import copies rather than moves.
Reverting the library choice itself is cheap only until the first store lands
on it, which is 20260801-120412.

**For the lane.**

The work splits into four tasks rather than one, in dependency order:
20260729-102147 (engine core), 20260801-120404 (Alembic runner and the
`projects` schema), 20260801-120407 (legacy import, unwired), 20260801-120412
(project store cutover, which wires it).

The import lands BEFORE the cutover. The reverse order strands an operator's
`projects.json`, and running the import at startup while `projects.py` still
writes JSON would lose any project created between the two tasks.
